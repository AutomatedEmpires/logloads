### F2 — P1 money/integrity: a recorded delivery could be cancelled away (EXECUTED)

The driver can record what was delivered as soon as the trip is `at_destination`.
Until the trip reaches `completed`, the assignment is still "active". The cancel
guards (`cancelAssignmentWithPolicy`, plus the `cancelled` branch of trip
progression) refused only a **confirmed** completion. That left two holes:

1. a host could cancel a haul after the driver had already recorded the
   delivery (`submitted`) or after the host had disputed it (`disputed`); and
2. either side could cancel while the truck sat at the mill.

Either way the delivery record was wiped, capacity went back on the board, and
the trip never completed. So the host's 5% fee never accrued, and the driver's
haul history lost a load that really moved. The implementation spec already
names this as forbidden (`docs/archive/marketplace-implementation-spec.md` §(d3)). Both
cockpits still showed a Cancel control at that point.

Action: one service predicate refuses cancellation in either of these states:
- the trip status is `at_destination`, `unloading` or `completed`; or
- the completion status is not `pending`.

It covers both cancel paths and both sides. The way out at the mill is the one
that already exists: the driver records the delivery, or an exception such as
rejected at scale. Then the host confirms or disputes. Driver and host UIs hide
Cancel in the same states. Each refusal has a negative-control test.

### F3 — P2 honesty: notification and error copy promising things that don't exist (EXECUTED)

- The host's "Capacity request received" notification body printed the raw
  requesting **organization UUID**.
  (`operating-network.ts`: `${context.organizationId} requested …`).
- The driver's "Not selected" notification said capacity is available "if the
  host reopens the decision". No reopen action exists. Capacity is restored the
  moment the request is declined, and the driver can request again right away.
  The body also hardcoded "went to another truck", whatever reason the host gave.
- A confirmed completion refuses edits with "ask the host to reopen it". No
  reopen path exists.

Action: name the driver and their organization; state the host's actual reason
and the real next step; replace the reopen instruction with the real recovery
path, which is messaging the host.

### F6 — Founder decision required: dispute counter-figure and auto-confirm

Spec §(b)/(c) describes three things:
- auto-confirming a submitted delivery after a disclosed 72h window;
- requiring the host to state a counter-figure when disputing; and
- a 336h timeout to resolve a dispute.

None of these is implemented. Today a host can dispute without a counter-figure
and leave the record `disputed` forever, so the fee never accrues and the driver's
history never settles. Auto-confirm turns host silence into a billable event,
which is a commercial and legal lever. Don't build it without a dated founder
decision. **Not executed.**

### F7 — P3: seed-only allocation modes

`open_claim` and `dispatcher_assignment` exist in the schema and in seed loads.
Host publishing always writes `request_approval`, and no service path lets a
dispatcher assign a driver directly. On seed loads the driver sees "A dispatcher
assigns this haul", a promise no real host can make. A real host can't reach this
state. Either remove the modes or build the assignment path when an acceptance
criterion needs it.
